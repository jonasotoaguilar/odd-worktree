# prs: a `/prs` pull request panel, the GITHUB rail wiring and cross-links

Feature: a `/prs` panel cloned from `/issues` for pull requests, joined to the GITHUB rail section, with clickable cross-links between both panels and an `Enter` insert in both.

## Specs

- **S1** — The panel. "un nuevo panel de comando que sera igual en diseno al de issues, pero lo que mostrara sera las pr/pull request y tendra 3 secciones principal, la de "My Pull Request", "Needs My Review", "Involved"": the PRs I created, the ones assigned to me to review, and the ones I take part in (commented, etc.). "con "g" cambias a ver "all prs" y con la misma volvemos."
- **S2** — Actions, permission-gated like issues: comment, add labels, add issues ("agregar issues" = the Development relation), merge, close PR, and assign (a toggle: it also unassigns). Merge confirms "commit message, description y tipo de merge si se permite (merge, rebase, squash, solo los que esten disponibles, no siempre estan todos a veces es solo merge normal)". "las opciones que no tengo permisos para hacer no se permiten ni aparecen en keybindings."
- **S3** — The summary above the body: who created it, assigned reviewers, linked issues, created/updated ago, labels, etc.; "de forma resumida los changes y checks": +/- lines, how many commits, how many checks ran, whether one failed, the changes/checks summary. Open on the web, like issues. Search "similar al de issues", including the scrolling.
- **S4** — The rail. In customize the section is named "github" (it was "issues"); the rail shows PRs next to issues (my PRs + needs review) as "n issues · n pr".
- **S5** — Rail click. An issue row that has a linked PR opens the PR panel on its related PR, not the issue; "se prioriza needs review sobre my pull request si la pr pertenece a ambas". Loading as fast as issues: "el loading en background en start si sidebar esta activa y demas".
- **S6** — Cross-links. In the issues panel each linked PR is independent and clickable and opens that PR in the PR panel; in the PR panel each linked issue is independent and clickable and opens that issue in the issues panel.
- **S7** — `Enter` means "insert" in BOTH panels: it puts the issue or the PR into the chat input, formatted like "ISSUE #63" or "PR #87".

## Contract (fixed before T1-T4 start; the four units are parallel and share no file)

Everything mirrors `/issues`: same invariants (6 repository identity pinning, 7 capabilities fail closed on anything but a literal `true`, 9 fixed argv, 24-28 no session path waits on `gh`), same seams, same row/pane design. A writer reads the matching `/issues` module first and cloned behaviour keeps the `/issues` wording unless a spec says otherwise.

**Buckets.** `mine` (my pull requests, tab label `My Pull Request`), `review` (`Needs My Review`, `review-requested:@me`), `involved` (`Involved`, `involves:@me`), and the lazy `all` (`g` toggles into `all prs` and back, like issues). Search path (`repo:<r> is:pr is:open author:@me | review-requested:@me | involves:@me`) for the three; connection path (`pullRequests(states: OPEN)`) for `all`.

**Client (`lib/gh-prs.js`, T1) exports**, each returning `{ok:true,…}|{ok:false,error}`, repository pinning exactly as `lib/gh-issues.js` (reuse its seams `runGh`, `setGhRunner`, scope helpers by import, never by editing that file):
- `getPullRequestPage({bucket, cursor, query, pageSize, scope, viewer})` → `{ok, rows, hasMore, cursor, totalCount}`; `getPullRequestConnectionPage({cursor, pageSize, scope})` for `all`.
- `getPullRequest(number, {includeMetadata, scope})` → `{ok, pullRequest, comments}` where `pullRequest` = the row below plus `body`, `reactions`, `baseRefName`, `headRefName`, `additions`, `deletions`, `changedFiles`, `commits` (count), `committedAt`, `reviewers:[{login, state}]` (`state` is `REQUESTED|APPROVED|CHANGES_REQUESTED|COMMENTED|DISMISSED`), `linkedIssues:[number]` + `linkedIssuesTruncated`, `checks: {total, passed, failed, pending, state:'SUCCESS'|'FAILURE'|'PENDING'|'NONE', failing:[name]}`, `mergeable`, `mergeStateStatus`, `isDraft`, `reviewDecision`, `mergeMethods: {merge:bool, squash:bool, rebase:bool}` (repo-allowed ones only), `mergeDefaults: {merge:{subject,body}, squash:{subject,body}, rebase:{}}` (GitHub's own proposals, e.g. subject `Merge pull request #69 from owner/branch`, body = the PR title), `unavailable:[…]`, `metadataError`.
- Row (list and pane head): `{number, title, state, isDraft, author, labels:[{name,color}], assignees:[login], createdAt, updatedAt, url, commentsCount, reviewDecision}` — the issue row's keys, plus those PR ones.
- `viewerPermission` → capability map `pullRequestPermissions(permission)` → `{canEditLabels, canEditAssignees, canClosePullRequests, canMerge, canEditLinkedIssues}` (literal `true` or nothing; `canMerge` also needs a non-draft PR and at least one allowed method; read access only → all false, comments stay ungated like issues).
- Mutations: `commentPullRequest`, `listLabels`/`createLabel`/`editLabels` (re-export the issue ones if they work on PR numbers, else mirror), `listAssignableUsers`, `editAssignees` (toggle for the viewer), `closePullRequest`, `mergePullRequest(number, {method:'merge'|'squash'|'rebase', subject, body})` (argv `gh pr merge N --merge|--squash|--rebase [--subject S] [--body B]`, rebase takes neither; refuses a method the repo did not allow), `editLinkedIssues(number, {add:[n], remove:[n]})` (GitHub has no mutation for the Development panel: it appends/removes a `Closes #N` line in the PR body with `gh pr edit --body`, preserving the rest byte for byte; the pane says so).
- Rail read `listRailPullRequests({scope, viewer})` → `{ok, mine:[{number, linkedIssues:[n]}], review:[{number, linkedIssues:[n]}]}` in ONE aliased GraphQL (counts must be exact: `issueCount`).

**Pure view (`lib/prs-view.js`, T2)**: `createPrsView(options)`, same options as `createIssuesView` with `loadPullRequestPage`, `loadPullRequest`, `loadLabels`, `loadAssignees`, `initialBucket`, `initialPullRequest`, and `actions` (`openBrowser`, `reload`, the mutations above as seams, plus `merge`, `close`, `editLinkedIssues`). Modes add `merge` (fields: type — only the allowed ones, the repository may allow just `merge` —, commit message, description, `Confirm merge` / `Cancel`) and `linkedIssues`. Footer keys hidden, and refusals sentence-for-sentence like issues, when the capability is not literally `true`. `lib/pr-preview.js` renders the pane in this order: `#N title`, `[open|draft]`, labels, `assignees:`, `reviewers:` (with state marks), `by <author> · created <ago> · updated <ago>`, reactions · comments, `linked issues: #12, #14` (each number its own click range), a `Changes` block (`N files changed +A -D`, `N commits <ago>`), a `Checks` block (`N checks`, failed count, summary, failing names), then the body and the comments.

**Seams both views obey (T2 and T3)**: `actions.insert(text)` — `Enter` in list mode calls it with `"PR #87"` (PR panel) or `"ISSUE #63"` (issues panel), then closes the panel; the same key keeps its existing meaning inside the search box, the editors and the confirm step. `actions.openLinked({kind:'issue'|'pullRequest', number})` — a click on one linked number inside the pane calls it for exactly that number; each number is its own click range, never the whole line. The footer lists `enter insert`.

**Rail (T4)**: `createIssuesSection` gains `loadPullRequests` (the seam T5 provides, shaped like `listRailPullRequests`), `rowLabel` default `'github'`, header `meta()` = `N issues · M pr` (`M` = distinct PR numbers in `mine` ∪ `review`; `· stale` kept; when the PR read is unavailable the header stays `N issues` as today), and the row's click calls `open(issueNumber, {pullRequest: <n>, pullRequestBucket: 'review'|'mine'|'all'})` when the issue has a linked PR (`review` wins over `mine`; a PR in neither is `all`), else the old call. `lib/prs-rail-store.js` persists the PR counts so a cold start paints them at once (same rules as `lib/issues-cache-store.js`: versioned document, temp file plus rename, never throws, read only from the async loader).
